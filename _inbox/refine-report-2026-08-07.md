### 過期概念複習題

- concept_id: async-processing
  - type: short_answer
  - difficulty: 2
  - question: In your own words, what is "Asynchronous Processing" and why does it exist / what problem does it solve?
  - answer: Instead of making the user wait while the server does something slow, accept the request immediately, put the work on a queue, and let a background worker handle it.
  - explanation: Slow operations (image resizing, sending emails, crunching analytics) block request threads and kill throughput. Async processing decouples the "accept the request" step from the "do the work" step, so the system stays responsive under load.
- concept_id: caching-strategies
  - type: short_answer
  - difficulty: 2
  - question: In your own words, what is "Caching Strategies" and why does it exist / what problem does it solve?
  - answer: Storing frequently accessed data in fast memory layers so you don't have to hit the slow database every time, with different update patterns depending on whether you prioritize speed or freshness.
  - explanation: Databases are slow under hot-spot traffic. A memory read (~100 ns) is orders of magnitude faster than a disk seek (~10 ms). Caching absorbs uneven loads and traffic spikes, but the hard part is keeping cached data in sync with the source of truth.
- concept_id: cap-theorem
  - type: short_answer
  - difficulty: 2
  - question: In your own words, what is "CAP Theorem" and why does it exist / what problem does it solve?
  - answer: In a distributed system, when a network partition happens you must choose between consistency (every read gets the latest write) and availability (every request gets a response).
  - explanation: Distributed systems spread data across multiple machines, and networks between them can fail. CAP forces you to consciously decide what your system does during a failure instead of hoping for the best.
- concept_id: database-replication
  - type: short_answer
  - difficulty: 2
  - question: In your own words, what is "Database Replication" and why does it exist / what problem does it solve?
  - answer: Automatically copying data from one database server (master) to one or more others so multiple servers hold identical data, enabling read scaling and failover.
  - explanation: A single database is both a performance bottleneck (all reads and writes hit one machine) and a single point of failure (if it dies, everything stops). Replication solves both.
- concept_id: database-sharding
  - type: short_answer
  - difficulty: 2
  - question: In your own words, what is "Database Sharding" and why does it exist / what problem does it solve?
  - answer: Splitting a database's rows across multiple independent database instances (shards) so each one handles only a slice of the data.
  - explanation: When a single database can't keep up with read/write volume or data size — even after adding read replicas and caching — sharding distributes the load across multiple machines, each with smaller indexes and better cache hit rates.
- concept_id: eventual-consistency
  - type: short_answer
  - difficulty: 2
  - question: In your own words, what is "Eventual Consistency" and why does it exist / what problem does it solve?
  - answer: After a write, all replicas will converge to the same value given enough time, but reads during the propagation window may return stale data.
  - explanation: Strong consistency requires every replica to confirm a write before responding, which is slow and reduces availability. Eventual consistency trades immediate accuracy for speed and uptime — the right choice when brief staleness is acceptable.
- concept_id: high-availability
  - type: short_answer
  - difficulty: 2
  - question: In your own words, what is "High Availability" and why does it exist / what problem does it solve?
  - answer: Designing every layer of a system with redundant pairs and automatic failover so the service stays up even when individual components die.
  - explanation: Redundant servers are useless if the single load balancer in front of them dies. HA ensures that no single component failure takes down the system, at every layer from disks to data centers.
- concept_id: horizontal-scaling
  - type: short_answer
  - difficulty: 2
  - question: In your own words, what is "Horizontal Scaling" and why does it exist / what problem does it solve?
  - answer: Adding more machines to share the work instead of making one machine bigger.
  - explanation: A single server has a hard ceiling on CPU, RAM, and disk. Upgrading it (vertical scaling) gets exponentially expensive and still has a max. Horizontal scaling sidesteps this by spreading load across many cheap commodity machines.
- concept_id: load-balancing
  - type: short_answer
  - difficulty: 2
  - question: In your own words, what is "Load Balancing" and why does it exist / what problem does it solve?
  - answer: A load balancer sits between clients and a group of servers, forwarding each request to a healthy server so no single machine gets overwhelmed and there's no single point of failure.
  - explanation: One server can only handle so much traffic, and if it dies everything goes down. A load balancer spreads requests across multiple servers, checks which ones are healthy, and can handle SSL encryption so backend servers don't have to.
- concept_id: microservices
  - type: short_answer
  - difficulty: 2
  - question: In your own words, what is "Microservices Architecture" and why does it exist / what problem does it solve?
  - answer: Breaking a big application into small, independent services that each do one thing, deploy separately, and talk to each other over the network.
  - explanation: In a monolith, one team's change can break everything, scaling means scaling the whole app, and a single bug can take down the entire system. Microservices let teams own, deploy, and scale their piece independently.
- concept_id: raid-storage
  - type: short_answer
  - difficulty: 2
  - question: In your own words, what is "RAID Storage" and why does it exist / what problem does it solve?
  - answer: Combining multiple hard drives into one logical unit to get speed (striping), redundancy (mirroring/parity), or both — so a single disk failure doesn't lose data.
  - explanation: Hard drives fail. RAID protects against disk-level data loss without requiring application changes. It's the hardware-level answer to "what if a disk dies?"
- concept_id: single-point-of-failure
  - type: short_answer
  - difficulty: 2
  - question: In your own words, what is "Single Point of Failure" and why does it exist / what problem does it solve?
  - answer: Any component whose failure alone would take down the entire system — the weakest link that makes all other redundancy pointless.
  - explanation: SPOF analysis is a thinking discipline, not a technology. Every time you solve one scaling problem, you risk creating a new SPOF. Identifying them is the first step to building resilient systems.
- concept_id: ssl-termination
  - type: short_answer
  - difficulty: 2
  - question: In your own words, what is "SSL Termination" and why does it exist / what problem does it solve?
  - answer: Decrypting HTTPS traffic at the load balancer so backend servers communicate over plain HTTP, centralizing certificate management and offloading crypto overhead.
  - explanation: HTTPS is essential for user-facing traffic, but performing TLS handshakes on every backend server wastes CPU and makes certificate deployment a pain. Terminating SSL at one point simplifies operations.
- concept_id: sticky-sessions
  - type: short_answer
  - difficulty: 2

- concept_id: llm-program-distillation
  - type: short_answer
  - difficulty: 2
  - question: In your own words, what is "LLM Program Distillation" and why does it exist / what problem does it solve?
  - answer: LLM program distillation uses a large, expensive model to generate high-quality (input, output) training pairs from a bootstrapped program, then fine-tunes a small, cheap model on those pairs — transferring the large model's task-specific behavior at a fraction of the inference cost.
  - explanation: The gap between frontier model quality and small model quality is often partially closable for narrow tasks. A GPT-4o-based DSPy program that has been optimized for a specific extraction or classification task generates reliable outputs on that task — those outputs become training data. Fine-tuning a Llama-3.2-1B on thousands of such examples teaches it to replicate the task-specific behavior, achieving similar quality at 100–1000× lower cost per inference call. Shopify used this approach (via GEPA + `BootstrapFinetune`) to achieve a 550× cost reduction on product attribute extraction. The mechanics in DSPy: (1) compile a teacher program with `BootstrapFewShot` using a capable LLM; (2) run it on a large dataset to collect `(input_fields, output_fields)` pairs; (3) call `BootstrapFinetune.compile(student, teacher, trainset)` which submits a fine-tuning job to a provider (`LocalProvider` via SGLang+TRL, `DatabricksProvider`, `OpenAIProvider`); (4) the returned student program uses the fine-tuned model and requires zero or fewer few-shot examples because the behavior is now encoded in the weights. The key constraint: distillation only works well for tasks where the large model is already reliable — if the teacher has low quality, the fine-tuned student inherits that noise.

### 題目內容

**q-async-processing-001** (async-processing, multiple_choice, difficulty 1)
- question: What is the primary benefit of using a message queue for async processing?
- answer: It decouples slow work from the request-response cycle so the user gets an immediate response
- explanation: The app publishes a job to the queue and responds immediately. A background worker picks up the job later. The user isn't blocked waiting for the slow operation to complete.

**q-async-processing-002** (async-processing, short_answer, difficulty 2)
- question: What is back pressure in the context of message queues, and why is it important?
- answer: Back pressure limits the queue size and returns HTTP 503 when full, with clients retrying via exponential backoff. It prevents memory exhaustion and cascading failures.
- explanation: Without back pressure, an unbounded queue can consume all available memory, cause disk thrashing, and degrade performance for all jobs. Back pressure keeps the system stable under overload.

**q-async-processing-003** (async-processing, application, difficulty 2)
- question: A user uploads a profile photo. The server needs to resize it into 5 different dimensions. Should this be done synchronously in the upload request or asynchronously? Why?
- answer: Asynchronously. Enqueue a resize job and return a success response immediately. A worker processes the resizing in the background. The user doesn't wait for 5 resize operations.
- explanation: Image resizing is CPU-intensive and slow. Doing it synchronously blocks the request thread and makes the upload feel sluggish. Async processing lets the user continue while the work happens in the background.

**q-caching-strategies-001** (caching-strategies, multiple_choice, difficulty 1)
- question: In the cache-aside pattern, what happens on a cache miss?
- answer: The application queries the database, then writes the result to the cache
- explanation: In cache-aside (lazy loading), the cache doesn't interact with the database directly. The application checks the cache, and on a miss, it reads from the DB and populates the cache for future requests.

**q-caching-strategies-002** (caching-strategies, short_answer, difficulty 2)
- question: What is the main risk of the write-behind (write-back) caching pattern?
- answer: Data loss — if the cache crashes before asynchronously flushing writes to the database, those writes are lost.
- explanation: Write-behind improves write performance by batching async writes to the DB, but the cache is the only copy of recent writes until the flush completes. A crash in that window means data loss.

**q-caching-strategies-003** (caching-strategies, application, difficulty 3)
- question: A user updates their profile bio. With cache-aside, other users still see the old bio for several minutes. How would you reduce this staleness without switching to write-through?
- answer: Explicitly invalidate or update the cache entry when the write occurs, rather than waiting for TTL expiry.
- explanation: Cache-aside relies on TTL for freshness by default. Adding explicit invalidation on writes (delete the cache key after DB update) gives near-immediate consistency without the write latency penalty of write-through.

**q-cap-theorem-001** (cap-theorem, multiple_choice, difficulty 1)
- question: According to the CAP theorem, since network partitions are inevitable, what is the real trade-off a distributed system must make?
- answer: Between consistency and availability
- explanation: Network partitions are unavoidable, so partition tolerance is mandatory. The CAP theorem says you must then choose: CP (consistency — risk timeouts) or AP (availability — risk stale reads).

**q-cap-theorem-002** (cap-theorem, short_answer, difficulty 2)
- question: Give one example of a CP system and one example of an AP system.
- answer: CP: traditional RDBMS with ACID transactions (e.g., PostgreSQL). AP: Cassandra, DynamoDB, or DNS.
- explanation: CP systems prioritize correctness — they may return errors during partitions rather than stale data. AP systems prioritize uptime — they return the best available data even if it's not the latest.

**q-cap-theorem-003** (cap-theorem, application, difficulty 3)
- question: You're designing an inventory system for a flash sale where overselling is unacceptable. Would you choose a CP or AP architecture, and what is the user-facing consequence?
- answer: CP — the system may return errors or timeouts during a network partition, but it will never show incorrect stock counts that lead to overselling.
- explanation: Inventory requires atomic reads and writes. A CP system ensures every read reflects the latest write. The trade-off is that during a partition, some requests may fail rather than return stale stock data.

**q-database-replication-001** (database-replication, multiple_choice, difficulty 1)
- question: In master-slave database replication, which server handles write operations?
- answer: Only the master
- explanation: In master-slave replication, the master handles all writes and replicates changes to slaves. Slaves handle read queries only. This makes the master a single point of failure for writes.
