# Highlights

- `p. 97, Section: Understand harness costs` Runtime billing uses per-second active consumption: CPU cost is consumed vCPU-seconds / 3,600 × the vCPU-hour rate, and model/tool I/O waits don't incur CPU charges when no other process uses CPU — but memory remains billable while the session runs.
- `p. 99, Section: Control cost with limits` Hard caps exist to stop a runaway agent regardless of its own logic: `maxIterations` (default 75), `timeoutSeconds` (default 3600), `maxTokens`, `idleRuntimeSessionTimeout` (default 900), and `maxLifetime` (default 28800) — all optional, all overridable per invocation.
- `p. 101, Section: AgentCore harness versioning and endpoints` Every harness update creates a new, complete, immutable version; the `DEFAULT` endpoint auto-updates to the latest version, but any other named endpoint (e.g., a production endpoint) must be explicitly repointed.
- `p. 473 and p. 503, Section: Invocation error handling / Input validation` A `prompt` field left untyped can carry a non-string value containing a `toolUse` content block; if the agent framework accepts it, the framework may dispatch the named tool directly, bypassing model reasoning, guardrails, and system-prompt enforcement entirely. The fix is an explicit `isinstance(prompt, str)` check or a schema that types the field as `str`, not `Any` — a default value in `.get("prompt", default)` does not reject a malformed input.
- `p. 502, Section: Confused deputy prevention` Add `aws:SourceArn` and `aws:SourceAccount` conditions to an execution role's trust policy so only a specific AgentCore resource — not any AgentCore resource in any account — can assume it.
- `p. 874, Section: Resource-based policies and cross-account access` Cross-account access to a runtime requires resource-based policies on both the runtime and its endpoint; if either resource lacks an explicit allow, the request is denied, and an explicit deny anywhere always wins.
- `p. 954-967, Section: Front your runtime with an AgentCore Gateway` A policy-enforcing Gateway in front of a Runtime only protects traffic that actually flows through it — if the Runtime can still be invoked directly, every Gateway policy, guardrail, and interceptor is bypassed entirely.
- `p. 1988, Section: Add rate limits to a gateway` Gateway rate limits use fail-open behavior by default: if the rate-limit service is unavailable or a dimension can't be resolved, the request is allowed through — the documentation explicitly warns not to rely on rate limits as a security boundary.
- `p. 1971-1973, Section: Policy in AgentCore overview` Policy in AgentCore intercepts all agent traffic through the Gateway and evaluates it against Cedar policies before allowing tool access — moving authorization outside the agent's own code so enforcement is deterministic regardless of how the agent is implemented.
- `p. 1992, Section: Policy engine` The policy engine applies default-deny and forbid-wins semantics automatically: a request is allowed only if a policy permits it, and a single forbid from any active policy denies it.
- `p. 1991-1992, Section: Dogwood / Temporal policies` Dogwood is Cedar-compatible (every valid Cedar policy is also valid Dogwood) and adds session-aware temporal conditions — requiring a prior approval, limiting how often an action runs, or keeping a running total under a threshold — evaluated against a policy session.
- `p. 2093-2094, Section: How LOG_ONLY mode works` A policy set to `LOG_ONLY` is evaluated on every request and reported in traces and CloudWatch metrics, but never contributes to the enforced decision; the system also reports which `LOG_ONLY` policies would have flipped the decision had they been active, as the key signal for promotion safety.
- `p. 2637-2638, Section: A/B testing` A/B tests split live production traffic at the Gateway with sticky-by-session-ID routing, score each session with online evaluation, and compute per-evaluator statistical significance (p-value below 0.05 indicates a significant difference) before a team promotes the treatment variant.
- `p. 2546, Section: AgentCore optimization: how it works` Configuration bundles are versioned, immutable snapshots of agent configuration (system prompts, model IDs, tool descriptions) that decouple behavioral changes from code deployment — optional, since a separate runtime endpoint can also be used to validate a change.
