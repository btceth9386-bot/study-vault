# Highlights

- `p. 1` AgentCore works with any open-source agent framework (CrewAI, LangGraph, LlamaIndex, Strands) and any foundation model, so teams don't have to trade open-source flexibility for enterprise security.
- `p. 139-142, Section: Harness vs. Runtime` For nearly every feature the pattern is the same: Harness gives it through configuration with no code, Runtime gives it through code you write with the AgentCore SDK.
- `p. 167-168, Section: Runtime protocol comparison` Runtime supports four wire protocols side by side — HTTP (port 8080), MCP (port 8000), A2A (port 9000), and AG-UI (port 8080) — each with its own message format and mount path.
- `p. 183-186, Section: A2A protocol contract` An A2A server must run on port 9000 as an ARM64 container, speak JSON-RPC 2.0, and expose `/.well-known/agent-card.json` for discovery and `/ping` for health.
- `p. 380-382, Section: Isolated sessions and session lifecycle` Each session gets its own dedicated microVM with isolated compute, memory, and filesystem; the entire microVM is terminated and memory sanitized when the session ends.
- `p. 383, Section: Session headers by protocol` AgentCore routes requests to the same microVM using a protocol-specific session header; without a consistent session ID, each request may land on a new microVM and pay a cold-start penalty.
- `p. 427-428, Section: Asynchronous and long-running agents` The `/ping` endpoint's `HealthyBusy` status keeps a long-running session alive past the idle timeout without a separate task-tracking system — but a `time_of_last_update` that advances on every ping defeats the timeout entirely.
- `p. 532-536, Section: AgentCore Memory overview` Short-term memory captures turn-by-turn context within one session; long-term memory asynchronously extracts and consolidates insights (preferences, facts, summaries) that persist across sessions.
- `p. 533, Section: Common use cases of memory` A team of AI agents managing a supply chain shares memory to synchronize inventory levels, anticipate demand, and optimize logistics — an explicit multi-agent memory-sharing use case.
- `p. 586-587, Section: Long-term memory organization` Namespaces should end in a trailing slash (e.g., `/actors/Alice/` not `/actors/Alice`) to prevent prefix collisions in multi-tenant applications, and can be used directly as IAM condition keys.
- `p. 599-601, Section: Cross-account memory access` A memory resource in one AWS account can grant data-plane access to principals in another account via a resource-based policy, evaluated alongside the caller's own identity-based policy.
- `p. 610, Section: Long-term memory vs. RAG` Long-term memory retains who the user is and what happened in previous sessions; RAG retrieves authoritative, current information from large-scale repositories — the two are complementary.
- `p. 718, Section: Memory poisoning or prompt injection` Because long-term memory extraction runs via an LLM, poisoned conversational input can produce corrupted memory stores and manipulated future responses — prevention belongs at the `CreateEvent` input-validation boundary, following AWS's shared responsibility model.
- `p. 2716-2717, Section: AWS Agent Registry` Without a central catalog, teams re-build MCP servers and agents that already exist simply because they can't discover them — Agent Registry solves this with a publish → approve → discover workflow.
- `p. 2719, Section: Discovering resources via the Registry's MCP Server` Each registry exposes its own MCP-compatible endpoint, so any MCP client — including another agent — can search and discover registered resources using standard protocol calls, no AWS SDK required.
