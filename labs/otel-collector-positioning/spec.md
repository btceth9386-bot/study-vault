# Lab: OpenTelemetry Positioning — Where the Collector Sits

- **Concepts**: [[telemetry-signal-model]], [[collector-pipeline-architecture]], [[otlp-vendor-neutral-telemetry-protocol]], [[opentelemetry-api-sdk-separation]]
- **Tools**: OpenTelemetry Collector (contrib), Prometheus, Grafana Tempo, Grafana, Docker Compose
- **Setup mode**: local-mock
- **Time box**: 45–75 min
- **Starting knowledge**: You can name "trace" and "metric" as different kinds of telemetry, and you've heard of Prometheus, Tempo, and Grafana as separate tools without necessarily knowing which layer each one occupies. You do not need prior Collector config experience.

## Quick primer

"OpenTelemetry" is not a dashboard and not a database — it doesn't store or display anything. It is three things stacked on top of each other, and this lab makes you feel the seam between each layer:

1. **Instrumentation (API + SDK)** — your app calls the OTel API to create spans and metric instruments ([[opentelemetry-api-sdk-separation]]). The SDK decides how that data is processed and exported. The app never imports "Prometheus" or "Tempo" — it only knows about OTel.
2. **Transport (OTLP)** — the SDK ships that data over the network as OTLP, a vendor-neutral wire format ([[otlp-vendor-neutral-telemetry-protocol]]). OTLP standardizes *how bytes move*, not what any backend does with them.
3. **Collector (pipelines)** — a separate process receives OTLP and decides, per signal, where it goes next: a named pipeline per signal type, each with receivers → processors → exporters ([[collector-pipeline-architecture]], [[telemetry-signal-model]]). This is the only layer that knows both "OTel" and "Prometheus/Tempo" exist.
4. **Backends + Grafana** — Prometheus stores and queries metrics only. Tempo stores and queries traces only. Grafana queries both through separate datasource plugins and renders them; Grafana itself never receives OTLP and stores nothing.

The lab's one config decision — wiring `service.pipelines` in the Collector — **is** layer 3. Get it right and each signal lands in the backend built for it. Get it wrong (the failure case) and you learn exactly why "Prometheus + Grafana" alone can never show you a trace.

## Goal

Prove, by configuring one file, that OpenTelemetry is the neutral instrumentation-and-routing layer sitting *upstream* of Prometheus, Tempo, and Grafana — not a replacement for any of them, and not the same layer as any of them.

## Your core task

Open `collector/otel-collector-config.yaml`. Fill in the two `exporters: []` lines under `service.pipelines`:

```yaml
service:
  pipelines:
    metrics:
      receivers: [otlp]
      processors: [batch]
      exporters: [] # TODO: YOUR CORE — route metrics to the metrics-only backend

    traces:
      receivers: [otlp]
      processors: [batch]
      exporters: [] # TODO: YOUR CORE — route traces to the traces-only backend
```

Both exporter names you need (`prometheus` and `otlp/tempo`) are already defined earlier in the same file, under `exporters:`. The decision is entirely "which name goes in which list" — that decision *is* the lesson: each signal type has exactly one backend built to hold it, and the Collector is where that match gets made.

## Failure / comparison case

Run `./scripts/failure-case.sh`. It starts the Collector once, standalone, using `collector/otel-collector-config.failure-case.yaml` — identical to your file except the `traces` pipeline is wired to the `prometheus` exporter instead of `otlp/tempo`.

The Collector does not start a broken pipeline and silently drop traces at runtime. It refuses to start at all:

```
Error: failed to build pipelines: failed to create "prometheus" exporter for data type "traces": telemetry type is not supported
```

Exit code is nonzero; no ports ever open. This is the concrete answer to "why can't I just point traces at Prometheus and skip Tempo": Prometheus is a metrics-only backend by construction — its exporter component literally does not implement a traces data-consumer interface — so the Collector catches the mismatch at pipeline-build time, before any network listener starts. This is also why "Prometheus + Grafana" alone, with no Collector and no Tempo, structurally cannot show you a trace: there is no traces-capable backend anywhere in that stack.

**Third signal, not built here:** logs follow the identical pattern — a `loki` exporter and a `logs: { receivers: [otlp], exporters: [loki] }` pipeline, same file, same shape. It's omitted to keep this lab's core task to one decision; see the review site for the one-paragraph explanation.

**Also not built here (extension, not required):** [[ottl-declarative-telemetry-transformation]] lets a processor rewrite or filter telemetry *inside* a pipeline (e.g., redact an attribute before export) — a different concern from *which* pipeline a signal takes. Worth knowing exists; not part of this lab's core task.
